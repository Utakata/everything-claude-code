# Progress Sync Contract（進捗同期契約）

ECC 2.0 は、GitHub、Linear、ローカルハンドオフ、リポジトリロードマップにまたがる実行状態を追跡します。この契約は、ステータス更新がレーンを最新であると主張できる前に必要となる最小限のエビデンスを定義します。

## 真実のソース

| サーフェス | 役割 | 現在のルール |
| --- | --- | --- |
| GitHub PR/issue/discussion | 公開キューとレビュー状態 | すべての重要なマージバッチの前、およびリリース承認の前に、ライブのカウントを再チェックする。 |
| Linear プロジェクト | エグゼクティブロードマップとステークホルダーのステータス更新 | issue の容量が issue 作成をブロックしている間は、プロジェクトのステータス更新を投稿する。ワークスペースの容量が利用可能な場合にのみ、issue を作成/再利用する。 |
| ローカルハンドオフ | 耐久性のあるオペレーターの継続性 | すべてのマージバッチ、キューのドレイン、スキップされたリリースゲート、またはブロックされた外部アクションの後に、アクティブなハンドオフを更新する。 |
| リポジトリロードマップ | 監査可能な計画ミラー | `docs/ECC-2.0-GA-ROADMAP.md` を、マージされた PR のエビデンスと未解決のゲートに整合させ続ける。 |
| `scripts/work-items.js` | ローカルトラッカーブリッジ | ステータススナップショットとブロックされたフォローアップのために、GitHub PR/issue を SQLite の work-items ストアに同期する。 |

## フローレーン

リポジトリミラーは、ECC の作業が1つの未分化なバックログに崩壊しないよう、以下のフローレーンを使用します：

- キュー衛生と stale 作業の救済
- リリース、ネーミング、プラグイン公開、アナウンス
- ハーネスアダプター準拠
- ローカルオブザーバビリティ、HUD/ステータス、セッション制御
- Evaluator/RAG と自己改善ハーネスループ
- AgentShield エンタープライズセキュリティプラットフォーム
- ECC Tools の billing、PR リスクチェック、深い分析、Linear 同期
- レガシーアーティファクト監査と translator/manual-review の残務

各フローレーンには、1つのオーナーアーティファクト、1つの現在のエビデンスソース、1つの次のアクションが必要です。これら3つのフィールドのいずれかが欠けている場合、レーンは最新ではありません。

## 重要なマージバッチの更新

重要なマージバッチの後、Linear とハンドオフを以下で更新します：

1. 追跡対象の GitHub リポジトリの現在の公開キューカウント。
2. マージされた PR 番号、コミット ID、検証エビデンス。
3. 変更されたリリースゲート（もしあれば）。
4. 延期またはスキップされた作業と、その明示的な理由。
5. 次の1〜2つの実装スライス。

Linear の issue 容量が利用できない場合は、プレースホルダー issue を作成する代わりに、プロジェクトのステータス更新を使用します。issue 容量が利用可能な場合は、正確なタイトルの issue を作成または再利用し、リポジトリのエビデンスにリンクします。

## リアルタイムの境界

ローカルのリアルタイムパスは、デフォルトでファイルバックアップです：

- `node scripts/work-items.js sync-github --repo <owner/repo>` は、現在の
  GitHub PR と issue の状態を SQLite の work-items ストアにインポートします。
- `node scripts/status.js --json` と `node scripts/work-items.js list --json`
  は、HUD、ハンドオフ、または後の Linear 同期のためにローカル状態を公開します。
- Linear は外部のステータスサーフェスのままです；リポジトリはリリース準備完了のために
  ホステッドテレメトリを必要としません。

PostHog のようなホステッドテレメトリは後で追加できますが、第二の真実のソースになるのではなく、同じイベントモデルを消費する必要があります。

## リリースゲート

この契約だけから、公開、タグ付け、アナウンス、marketplace パッケージの提出、またはプラグインの利用可能性の主張を行わないでください。リリース準備には、依然として publication-readiness のエビデンスドキュメント、新鮮なキューチェック、パッケージチェック、プラグインチェック、および明示的なメンテナー承認が必要です。
