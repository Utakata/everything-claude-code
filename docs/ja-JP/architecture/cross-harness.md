# クロスハーネスアーキテクチャ

ECC は再利用可能なワークフローレイヤーです。ハーネスは実行サーフェスです。

目標は、エージェンティックな作業の耐久性のある部分を1つのリポジトリに保つことです：

- スキル
- ルールとインストラクション
- ハーネスがサポートする場合のフック
- MCP 設定
- インストールマニフェスト
- セッションとオーケストレーションのパターン

Claude Code、Codex、OpenCode、Cursor、Gemini、および将来のハーネスは、ツールごとに新しいワークフローモデルを要求するのではなく、それらの資産をエッジで適応させるべきです。

オペレーター向けのサポートマトリックスとスコアカードワークフローについては、
[ハーネスアダプター準拠マトリックス](harness-adapter-compliance.md) を参照してください。

## ポータビリティモデル

| サーフェス | 共有ソース | ハーネスアダプター | 現在のステータス |
|---------|---------------|-----------------|----------------|
| スキル | `skills/*/SKILL.md` | Claude プラグイン、Codex プラグイン、`.agents/skills`、Cursor スキルコピー、OpenCode プラグイン/設定 | ハーネス固有のパッケージングでサポート |
| ルールとインストラクション | `rules/`、`AGENTS.md`、翻訳ドキュメント | Claude ルールインストール、Codex `AGENTS.md`、Cursor ルール、OpenCode インストラクション | サポート、ただしハーネス間で同一ではない |
| フック | `hooks/hooks.json`、`scripts/hooks/` | Claude ネイティブフック、OpenCode プラグインイベント、Cursor フックアダプター | Claude/OpenCode/Cursor ではフックバックアップ；Codex ではインストラクションバックアップ |
| MCP | `.mcp.json`、`mcp-configs/` | ハーネスごとのネイティブ MCP 設定インポート | ハーネスが MCP を公開する場合にサポート |
| コマンド | `commands/`、CLI スクリプト | Claude スラッシュコマンド、互換シム、CLI エントリポイント | サポート、ただしコマンドセマンティクスは異なる |
| セッション | `ecc2/`、セッションアダプター、オーケストレーションスクリプト | TUI/デーモン、tmux/ワークツリーのオーケストレーション、ハーネス固有のランナー | アルファ |

## 変更なしで移動するもの

`SKILL.md` は最もポータブルな単位です。

良い ECC スキルは以下であるべきです：

- `name`、`description`、`origin` を持つ YAML フロントマターを使用する
- スキルをいつ使用するかを記述する
- シークレットを埋め込まずに、必要なツールまたはコネクターを述べる
- 例をリポジトリ相対または汎用に保つ
- セクションが明確にラベル付けされていない限り、ハーネス限定のコマンドの仮定を避ける

同じソーススキルは、主にインストラクション、制約、ワークフローの形であるため、複数のハーネスにインストールできます。

## 適応されるもの

各ハーネスは、異なるローディングと強制の挙動を持ちます：

- Claude Code はプラグイン資産をロードし、ネイティブのフック実行を持つ。
- Codex は `AGENTS.md`、プラグインメタデータ、スキル、MCP 設定を読むが、フックパリティはインストラクション駆動。
- OpenCode は、アダプターレイヤーを通じて ECC フックロジックを再利用できるプラグイン/イベントシステムを持つ。
- Cursor は独自のルールとフックのレイアウトを使用するため、ECC は `.cursor/` の下に翻訳されたサーフェスを維持する。
- Gemini サポートはインストール/インストラクション指向であり、完全なフックパリティではなく、互換性サーフェスとして扱うべき。

アダプターは薄いままであるべきです。共有の挙動は `skills/`、`rules/`、`hooks/`、`scripts/`、`mcp-configs/` に属します。

## Hermes の境界

Hermes は公開 ECC ランタイムではありません。

Hermes は、ECC 資産を消費できるオペレーターシェルです：

- 選択された ECC スキルを Hermes のスキルディレクトリにインポートする
- ツールアクセスに ECC MCP 規約を使用する
- チャット、CLI、cron、ハンドオフのワークフローを再利用可能な ECC パターンを通じてルーティングする
- 繰り返されるローカルオペレーター作業をサニタイズ済みの ECC スキルに蒸留し戻す

公開リポジトリは、ローカルの Hermes 状態ではなく、再利用可能なパターンを出荷すべきです。

出荷すべきもの：

- サニタイズ済みのセットアップドキュメント
- リポジトリ相対のデモプロンプト
- 汎用のオペレータースキル
- プライベートな認証情報に依存しない例

出荷すべきでないもの：

- OAuth トークンや API キー
- 生の `~/.hermes` エクスポート
- 個人のワークスペースメモリ
- プライベートデータセット
- レビューされていないローカル限定の自動化パック

## 実例

`skills/hermes-imports/SKILL.md` を、ハーネス横断で同じスキルソースとして使用します。

ワークフローは以下です：

1. 耐久性のある挙動を `skills/hermes-imports/SKILL.md` に一度作成する。
2. シークレット、ローカルパス、生のオペレーターメモリをスキルの外に保つ。
3. スキルがどのようにロードされるかを各ハーネスに適応させる。
4. ソーススキルとハーネス向けのメタデータを別々にテストする。

Claude Code は Claude プラグインサーフェスを通じてスキルを取得し、関連するフックをネイティブに強制できます。

Codex はリポジトリのインストラクション、`.codex-plugin/plugin.json`、MCP リファレンス設定を読みます。同じスキルソースが依然としてワークフローを記述しますが、Codex がネイティブのフックサーフェスを追加しない限り、フックパリティはインストラクションバックアップです。

OpenCode は OpenCode パッケージ/プラグインサーフェスを通じてスキルを取得します。イベント処理はアダプターレイヤーを通じて ECC フックロジックを再利用でき、スキルのテキストは変更されないままです。

変更が同じワークフローの3つのハーネスコピーを編集する必要がある場合、共有ソースが間違った場所にあります。ワークフローを `skills/` に戻し、ハーネスのエッジでローディング、イベントの形、またはコマンドルーティングのみを適応させます。

## 今日 vs 後で

今日サポート：

- `skills/` の共有スキルソース
- Claude Code プラグインパッケージング
- Codex プラグインメタデータと MCP リファレンス設定
- OpenCode パッケージ/プラグインサーフェス
- Cursor 適応のルール、フック、スキル
- アルファの Rust コントロールプレーンとしての `ecc2/`

まだ成熟中：

- すべてのハーネス間の正確なフックパリティ
- Hermes への自動スキル同期
- `ecc2/` のリリースパッケージング
- クロスハーネスのセッション resume セマンティクス
- より深いメモリとオペレーター計画のレイヤー

## 新しい作業のルール

ワークフローを追加するとき、耐久性のある挙動をまず ECC に置きます。

ハーネス固有のファイルは、以下のためだけに使用します：

- 共有資産のローディング
- イベントの形の適応
- コマンド名のマッピング
- プラットフォームの制限の処理

ワークフローが1つのハーネスでのみ機能する場合、その境界を直接文書化します。
