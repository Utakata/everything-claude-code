# Evaluator RAG プロトタイプ

ECC 2.0 は、ユーザーの Claude、Codex、OpenCode、dmux、Zed、またはターミナルのセットアップを盲目的に変更することなく、実際の作業から学習できる自己改善ハーネスループを必要とします。このプロトタイプは、そのループのための最小限の読み取り専用アーティファクトセットを定義します。

フィクスチャセットは
[`examples/evaluator-rag-prototype/`](../../examples/evaluator-rag-prototype/) にあります。
それは2026年5月の stale-PR クリーンアップと救済レーンから始まりました。なぜなら、そのレーンには実際の入力、実際の承認された作業、実際の却下された作業があるからです。コーパスには現在、billing/Marketplace 準備シナリオも含まれており、ローンチコピーがドライランのリリースエビデンスやロードマップの意図をライブの billing 状態として扱えないようになっています。CI 失敗診断シナリオは、エージェントが赤いチェックの修正を提案する前に必要な log-first ワークフローを追加します。ハーネス設定品質シナリオは、MCP、プラグイン、フック、コマンド、エージェント、アダプターの推奨を、セットアップガイダンスを変更する前にアダプターマトリックスに紐づけたままにします。AgentShield ポリシー例外シナリオは、セキュリティ例外を SARIF/レポートのエビデンス、owner フィールド、expiry 状態、修復か例外かの判断でゲートします。スキル品質エビデンスシナリオは、スキル修正が昇格される前に、観測された失敗またはフィードバックのエビデンス、動作する例、リファレンスセットのギャップ、検証コマンドを要求します。deep-analyzer エビデンスシナリオは、リポジトリまたはコミット分析の挙動が変更される前に、アナライザーコーパスのケース、期待出力の比較、リスク分類の証明を要求します。

## リファレンスの圧力

- Meta-Harness：ハーネス自体を、シナリオ仕様、検証器の結果、昇格されたプレイブックを持つ
  実験として扱う。
- Autocontext：インストールされたエージェント資産を変更する前に、トレース、レポート、
  アーティファクト、再利用可能な改善を保存する。
- Claude HUD：コンテキスト、ツール、todo、エージェントアクティビティ、チェック、リスクを公開し、
  evaluator が実行を事後に判断できるようにする。
- Hermes Agent：ローカルコマンドを隠すのではなく、スキル、メモリ、スケジューラーのような
  フォローアップ、ターミナルゲートウェイの挙動を明示的に保つ。
- dmux、Orca、Superset、Ghast：ワークツリー/セッションの状態を保持し、並列
  エージェント作業を比較、resume、またはクリーンにクローズできるようにする。
- ECC Tools：GitHub をあふれさせることなく、evaluator の findings を PR コメント、check run、Linear
  バックログ項目にルーティングする。

## アーティファクト契約

すべての evaluator/RAG の実行は、検証器がプレイブックを昇格させるまで読み取り専用です。

| アーティファクト | 目的 | フィクスチャ |
| --- | --- | --- |
| シナリオ仕様 | 目的、許可されたエビデンス、禁止されたアクション、pass/fail ゲートを宣言する。 | `scenario.json` |
| トレース | 観測、取得、提案、検証、昇格のイベントをキャプチャする。 | `trace.json` |
| レポート | スコア、エビデンスカバレッジ、リスク、推奨される次のアクションを要約する。 | `report.json` |
| 候補プレイブック | 後で再利用できるメンテナー所有のワークフローを記述する。 | `candidate-playbook.md` |
| 検証器の結果 | 具体的な理由とロールバックノートとともに候補を承認または却下する。 | `verifier-result.json` |

プロトタイプは意図的に取得をアクションから分離します。実行はクローズされた PR の差分、Linear のステータス、CI 履歴、ローカルドキュメントを取得できますが、evaluator パスの一部として設定をクローズ、マージ、公開、タグ付け、または書き換えることはできません。

## フェーズモデル

1. 現在のキュー、dirty なワークツリー、ブランチ状態、オープンな PR/issue、
   ディスカッション、CI 状態、リリースゲートを観測する。
2. 関連するリファレンスエビデンスを取得する：stale-salvage レジャーの行、以前の
   メンテナー PR、現在のドキュメント、アナライザーの findings、CI 失敗、ハーネス
   アダプターのルール。
3. ソースアトリビューションと期待される検証ゲートとともに、1つ以上のプレイブックを提案する。
4. 各プレイブックを明示的な承認および却下のルールに対して検証する。
5. blast radius を広げずにシナリオを改善する候補のみを昇格させる。
6. ロールバックガイダンスと未解決の manual-review 残務を記録する。

## 最初のシナリオ

最初のシナリオは `stale-pr-salvage-maintainer-branch` です。

これは、Affaan が2026年5月のクリーンアップ中に設定したルールをモデル化します：stale なクローズはキュー衛生であり、有用な作業の損失ではありません。有用なクローズされた PR の作業は、アトリビューション/バックリンクとともにメンテナー所有の PR に移植されるべきであり、生成された churn、一括ローカライゼーション、曖昧な translator 作業は盲目的な cherry-pick の対象外に留まります。

検証器は、以下を満たすメンテナー救済ブランチを承認します：

- ソース PR をクレジットする；
- 生のプライベートコンテキストと個人パスを避ける；
- translator レビューなしで stale な一括ローカライゼーションをインポートしない；
- 耐久性のあるレジャー更新を記録する；
- 通常のコード、ドキュメント、カタログの変更と同じ検証ゲートを実行する；
- リリース公開アクションを承認ゲートのままにする。

検証器は、以下の盲目的な cherry-pick の提案を却下します：

- stale な翻訳/ドキュメントの churn をまるごとインポートする；
- 現在のカタログ/インストールアーキテクチャをスキップする；
- アトリビューションを欠く；
- テストまたはレジャー更新を欠く；
- リリースまたはプラグイン公開の状態を変更する。

## コーパスフィクスチャ

ルートのフィクスチャファイルは、元の `stale-pr-salvage-maintainer-branch` プロトタイプを保持します。追加のシナリオは、同じ5アーティファクト契約を再利用する場合、サブディレクトリに存在できます。

現在のコーパス：

- `stale-pr-salvage-maintainer-branch`：アトリビューションと検証を伴うメンテナー所有の
  ブランチを通じて、有用なクローズされた PR 作業を回復する。
- `billing-marketplace-readiness`：公開コピーがそれらをライブと言う前に、billing、App、
  Marketplace のローンチの主張を検証する。
- `ci-failure-diagnosis`：CI 修正プレイブックが昇格される前に、失敗したジョブのログ、変更ファイルの
  スコープ、名指しされたリグレッションコマンドを要求する。
- `harness-config-quality`：ハーネスセットアップの推奨が昇格される前に、アダプター状態、
  install/onramp パス、検証コマンド、リスクノート、設定保持の挙動を要求する。
- `agentshield-policy-exception`：ポリシー例外が昇格される前に、AgentShield SARIF またはレポートの
  エビデンス、ポリシーパックのソース、owner/ticket/scope/expiry フィールド、期限切れ
  例外の強制を要求する。
- `skill-quality-evidence`：スキル修正が昇格される前に、焦点を絞ったスキルスコープ、観測された失敗または
  ユーザーフィードバックのエビデンス、examples/リファレンスセットのカバレッジ、検証コマンド、
  公開の安全性を要求する。
- `deep-analyzer-evidence`：deep-analysis の挙動が昇格される前に、メンテナンスされたアナライザーコーパスのケース、
  期待出力の比較、代表的なリポジトリ/コミット履歴、リグレッションコマンドを要求する。

## ECC Tools のマッピング

ECC Tools はすでに、取得、埋め込み、ランキング、evaluator の変更について、欠けている RAG/evaluator エビデンスにフラグを立てます。このプロトタイプは、それらのチェックにターゲットの形を与えます：

- `scenario.json` はアナライザーコーパスの入力にマップされる。
- `trace.json` はゴールデントレースと実行テレメトリにマップされる。
- `report.json` は PR コメントサマリーと Linear バックログサマリーにマップされる。
- `candidate-playbook.md` は提案されたフォローアップ PR 本文にマップされる。
- `verifier-result.json` は pass/fail の check-run エビデンスにマップされる。

将来の ECC Tools の作業は、ホステッド取得やモデルバックアップの判断を追加する前に、これらのアーティファクトをフィクスチャの形として消費すべきです。ローカルプロトタイプは、いかなる有料 API やベクトルストアが導入される前にも契約を証明するのに十分です。

## 昇格ルール

候補は、以下の場合にのみ昇格できます：

- 検証器の結果が `accepted` である；
- 少なくとも1つの却下された候補が、検証器が no と言えることを証明する；
- すべてのソース PR またはリファレンスアーティファクトにアトリビューションがある；
- 提案されたアクションがメンテナー所有で可逆である；
- 検証コマンドが名指しされている；
- 未解決の translator、release、billing、または publication の項目が、
  別途承認されるまでブロックされたままである。

## 次の拡張

ローカルの evaluator/RAG コーパスは、現在のエビデンスバケットをカバーするようになりました。将来の作業は、ホステッド取得、ベクトルストレージ、モデルバックアップの判断、または自動化された check-run 昇格を追加する前に、これらのフィクスチャを ECC Tools から消費すべきです。
