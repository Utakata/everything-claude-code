# ECC 2.0 オブザーバビリティ準備

ECC 2.0 は、より自律的になる前に観測可能であるべきです。ローカルのデフォルトは、opt-in でリポジトリが所有する準備ゲートであり、テレメトリをどこにも送信せずに、コアなシグナルが存在するかどうかをチェックします。

実行：

```bash
npm run observability:ready
node scripts/observability-readiness.js --format json
```

このゲートは決定論的で、CI で安全に実行できます。リポジトリのファイルのみをチェックし、リリースサーフェスがオペレーターの必要とするシグナルを公開できるかどうかを報告します。

## シグナルモデル

- ライブステータス：`scripts/loop-status.js` は JSON を出力し、アクティブなループを監視し、
  ダッシュボードまたはハンドオフのためにスナップショットを書き込めます。
- HUD/ステータス契約：`docs/architecture/hud-status-session-control.md` と
  `examples/hud-status-contract.json` は、コンテキスト、ツール呼び出し、アクティブなエージェント、
  todo、チェック、コスト、リスク、キュー、セッション制御、トラッカー同期のための
  ポータブルなペイロードを定義します。
- セッショントレース：`scripts/session-inspect.js` は、Claude、dmux、
  アダプターバックアップのセッションを検査し、正規のスナップショットを書き込めます。
- ハーネスベースライン：`scripts/harness-audit.js` は、ツールカバレッジ、コンテキスト効率、
  品質ゲート、メモリ永続化、eval カバレッジ、セキュリティガードレール、コスト効率のための
  繰り返し可能なスコアカードを提供します。
- ツールアクティビティ：`scripts/hooks/session-activity-tracker.js` は、ECC2 が同期できる
  ローカルの `tool-usage.jsonl` イベントを記録します。
- リスクレジャー：`ecc2/src/observability/mod.rs` は、ツール呼び出しをスコアリングし、
  レビューのためにページネートされたレジャーを保存します。
- 進捗同期：`docs/architecture/progress-sync-contract.md` は、マージバッチとリリースゲートレビューの間、
  GitHub、Linear、ローカルハンドオフ、リポジトリロードマップ、`scripts/work-items.js`
  がどのように整合を保つかを定義します。
- リリースセーフティ：`docs/releases/2.0.0-rc.1/publication-readiness.md`、
  ポストハードニングエビデンス、サプライチェーンインシデント対応、ワークフローセキュリティ
  検証、npm pack チェック、リリースサーフェステストは、いかなる公開タグ、パッケージ publish、
  プラグイン提出、アナウンスアクションの前にも存在しなければなりません。

## リファレンスの圧力

現在のエージェントツーリングエコシステムは、同じ運用ニーズに収束しつつあります：

- dmux、Orca、Superset は、分離されたワークツリーと、エージェント状態と
  merge/review の作業を1か所で見ることを強調します。
- Claude HUD は、コーディングループ内でコンテキスト、ツールアクティビティ、エージェントアクティビティ、
  todo の進捗を可視化します。
- Autocontext は、すべての実行を耐久性のあるトレース、レポート、アーティファクト、
  再利用可能な改善として記録します。
- Meta-Harness は、ハーネス自体を評価・改善するものとして扱い、
  それには proposer の挙動と結果のクリーンなログが必要です。
- Zed と OpenCode は、エージェント制御サーフェス、レビュー可能な変更、および
  ポータブルなプロジェクト知識を依然として保持すべきハーネス固有の設定を強調します。

ECC の答えは、デフォルトではホステッド分析への依存ではありません。最初のリリース候補ゲートは、ローカルでファイルバックアップです。ホステッドテレメトリは後で来ることができますが、ローカルのイベントモデルが信頼するに十分有用になった後のみです。

## オペレーターワークフロー

1. `npm run observability:ready` を実行する。
2. より広範なハーネススコアカードのために `npm run harness:audit -- --format json` を実行する。
3. より長い自律バッチの間、`node scripts/loop-status.js --json --write-dir .ecc/loop-status`
   を実行する。
4. 新しい HUD またはオペレーターダッシュボードを配線する前に、`examples/hud-status-contract.json` をレビューする。
5. どのセッションサーフェスが利用可能かを確認するために `node scripts/session-inspect.js --list-adapters` を実行する。
6. 追跡対象リポジトリのローカル work-item ステータスに頼る前に、`node scripts/work-items.js sync-github --repo <owner/repo>` を実行する。
7. 自律性を高める前に、リスクの高い操作、コンフリクト分析、ハンドオフレビューのために ECC2 のツールログを使用する。
8. いかなる公開リリースアクションの前にも、リリースセーフティのエビデンスチェックを再実行する：
   publication readiness、サプライチェーンインシデント対応、ワークフローセキュリティ
   検証、パッケージサーフェス、リリースサーフェステスト。

最終状態は実践的です：ECC により大きなマルチエージェントループを実行するよう求める前に、オペレーターは、システムがライブステータス、耐久性のあるセッショントレース、ベースラインスコアカード、ローカルのリスクレジャー、および GitHub、Linear、ハンドオフ、ロードマップのエビデンスが乖離しないよう保つ進捗同期契約を持っていることを証明できます。
