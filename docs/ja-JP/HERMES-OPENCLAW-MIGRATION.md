# Hermes / OpenClaw -> ECC 移行

このドキュメントは、Hermes または OpenClaw スタイルのオペレーターセットアップを現在の ECC モデルに移行するための公開移行ガイドです。

目標は、プライベートなオペレーターワークスペースをバイト単位で再現することではありません。

目標は、有用なワークフローサーフェスを保持することです：

- 再利用可能なスキル
- 安定した自動化のエントリポイント
- クロスハーネスのポータビリティ
- スケジューラー / リマインダー / ディスパッチ
- 耐久性のあるコンテキストとオペレーターメモリ

一方で、プライベートに留まるべき部分を削除します：

- シークレット
- 個人データセット
- アカウントトークン
- ローカル限定のビジネスアーティファクト

## 移行のテーゼ

Hermes と OpenClaw を、最終的なランタイムではなく、ソースシステムとして扱います。

ECC は耐久性のある公開システムです：

- スキル
- エージェント
- コマンド
- フック
- インストールサーフェス
- セッションアダプター
- ECC 2.0 コントロールプレーンの作業

Hermes と OpenClaw は、ECC ネイティブなサーフェスに蒸留できる繰り返しのオペレーターワークフローを含んでいるため、有用な入力です。

つまり、最短の安全なパスは以下です：

1. 再利用可能な挙動を抽出する
2. それを ECC ネイティブなスキル、フック、ドキュメント、またはアダプター作業に変換する
3. シークレットと個人データをリポジトリの外に保つ

## 現在のワークスペースモデル

現在のワークスペース分割を一貫して使用します：

- ライブなコード作業は `~/GitHub` 配下のクローンされたリポジトリで行われる
- リポジトリ固有のアクティブな実行コンテキストは、リポジトリレベルの `WORKING-CONTEXT.md` にある
- より広範な非コードのコンテキストは KB/アーカイブレイヤーに置ける
- 耐久性のあるマシン横断の真実は、GitHub、Linear、ナレッジベースを優先すべき

公開リポジトリの中に影のプライベートワークスペースを再構築しないでください。

## 変換マップ

### 1. スケジューラー / cron レイヤー

ソースの例：

- `cron/scheduler.py`
- `jobs.py`
- 定期的な準備またはアカウンタビリティのループ

以下に変換：

- 利用可能な場合は Claude ネイティブのスケジューリング
- ローカルの繰り返し可能性のための ECC フック / コマンド自動化
- issue `#1050` 配下の ECC 2.0 スケジューラー作業

現在、リポジトリはすでに適切な公開フレーミングを持っています：

- 低レイテンシのリポジトリローカル自動化のためのフック
- 明示的なオペレーターアクションのためのコマンド
- 将来の長期スケジューリング/コントロールプレーンとしての ECC 2.0

### 2. ゲートウェイ / ディスパッチレイヤー

ソースの例：

- Hermes ゲートウェイ
- モバイルディスパッチ / リモートナッジ
- アクティブなセッション間のオペレータールーティング

以下に変換：

- ECC セッションアダプターとコントロールプレーンの作業
- オーケストレーション/セッション検査コマンド
- 以下の配下の ECC 2.0 コントロールプレーンのバックログ：
  - `#1045`
  - `#1046`
  - `#1047`
  - `#1048`

公開リポジトリは、リモートオペレーターシェルがすでに完全に GA であるかのように装うのではなく、アダプターの境界とコントロールプレーンモデルを記述すべきです。

### 3. メモリレイヤー

ソースの例：

- `memory_tool.py`
- ローカルのオペレーターメモリ
- ビジネス / オペレーションのコンテキストストア

以下に変換：

- `knowledge-ops`
- リポジトリの `WORKING-CONTEXT.md`
- GitHub / Linear / KB バックアップの耐久性のあるコンテキスト
- `#1049` 配下の将来の深いメモリ作業

重要な区別は以下です：

- リポジトリの実行コンテキストはリポジトリの近くに属する
- より広範な非コードメモリは KB/アーカイブシステムに属する
- 公開リポジトリは、プライベートなメモリダンプを保存するのではなく、境界を文書化すべき

### 4. スキルレイヤー

ソースの例：

- Hermes スキル
- OpenClaw スキル
- 生成されたオペレータープレイブック

以下に変換：

- ワークフローが再利用可能な場合は ECC ネイティブのトップレベルスキル
- コンテンツが単なるテンプレートの場合は docs/examples
- 挙動が知識形状ではなく手続き的な場合はフックまたはコマンド

この方法で最近すでに救済された例：

- `knowledge-ops`
- `github-ops`
- `hookify-rules`
- `automation-audit-ops`
- `email-ops`
- `finance-billing-ops`
- `messages-ops`
- `research-ops`
- `terminal-ops`
- `ecc-tools-cost-audit`

### 5. ツール / サービスレイヤー

ソースの例：

- カスタムサービスラッパー
- API キーバックアップのローカルツール
- ブラウザ自動化のグルー

以下に変換：

- コネクターが存在する場合は MCP バックアップのサーフェス
- ワークフローロジックが真の資産である場合は ECC ネイティブのオペレータースキル
- 欠けている部分がセッション/ランタイムの調整である場合はアダプター/コントロールプレーンの作業

プライベートなワークフローがそれらに依存していたというだけで、不透明なサードパーティランタイムを ECC にインポートしないでください。

ワークフローが価値がある場合：

1. 挙動を理解する
2. 最小限の ECC ネイティブ版を再構築する
3. ローカルで必要な auth/コネクターを文書化する

## すでに公開で存在するもの

現在のリポジトリは、すでに移行の意味のある部分をカバーしています：

- ECC 2.0 アダプター/コントロールプレーン探索ドキュメント
- オーケストレーション/セッション検査の基盤
- オペレーターワークフローのスキル
- コスト / billing / ワークフロー監査のスキル
- クロスハーネスのインストールサーフェス
- 設定とエージェントサーフェスのスキャンのための AgentShield

これは、移行の問題がもはや「ゼロから始める」ものではないことを意味します。

それはほとんどの場合、以下です：

- 欠けているプライベートワークフローの蒸留
- 公開ドキュメントの明確化
- ECC 2.0 オペレーター/コントロールプレーンの構築の継続

ECC 2.0 は現在、境界付きの移行監査のエントリポイントを出荷します：

- `ecc migrate audit --source ~/.hermes`
- `ecc migrate plan --source ~/.hermes --output migration-plan.md`
- `ecc migrate scaffold --source ~/.hermes --output-dir migration-artifacts`
- `ecc migrate import-skills --source ~/.hermes --output-dir migration-artifacts/skills`
- `ecc migrate import-tools --source ~/.hermes --output-dir migration-artifacts/tools`
- `ecc migrate import-plugins --source ~/.hermes --output-dir migration-artifacts/plugins`
- `ecc migrate import-schedules --source ~/.hermes --dry-run`
- `ecc migrate import-remote --source ~/.hermes --dry-run`
- `ecc migrate import-env --source ~/.hermes --dry-run`
- `ecc migrate import-memory --source ~/.hermes`

まずこれを使用して、レガシーワークスペースをインベントリ化し、検出されたサーフェスを現在の ECC2 スケジューラー、リモートディスパッチ、メモリグラフ、テンプレート、手動変換レーンにマップします。

## 推奨される立ち上げ順序

1. 公開 ECC リポジトリを正規の再利用可能なレイヤーとして保つ。
2. 再利用可能な Hermes/OpenClaw ワークフローを、一度に1レーンずつ ECC ネイティブなスキルに移植する。
3. プライベートな auth と個人コンテキストをリポジトリの外に保つ。
4. GitHub / Linear / KB システムを耐久性のある真実として使用する。
5. ECC 2.0 を、完成品としてではなく、ネイティブなオペレーターシェルへのパスとして扱う。

## 決定ルール

Hermes または OpenClaw のアーティファクトをレビューするとき、以下を問います：

1. これはオペレーター横断で再利用可能か、それとも個人的なものだけか？
2. その資産は主に知識、手続き、それともランタイムの挙動か？
3. それは以下のいずれになるべきか：
   - スキル
   - コマンド
   - フック
   - ドキュメント/例
   - コントロールプレーンの issue
4. それを公開で出荷すると、シークレット、プライベートデータセット、個人の運用状態を漏らすか？

再利用可能なサーフェスのみを出荷してください。
