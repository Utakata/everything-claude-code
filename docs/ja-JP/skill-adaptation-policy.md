# スキル適応ポリシー

ECC は外部リポジトリからのアイデアを受け入れますが、出荷されるスキルは ECC ネイティブなサーフェスになる必要があります。

## デフォルトルール

コントリビューションが別のオープンソースリポジトリ、プロンプトパック、プラグイン、ハーネス、または個人設定から始まる場合：

- 根底にあるアイデア、ワークフロー、または構造をコピーする
- それを ECC の現在のインストールサーフェス、検証フロー、リポジトリ規約に適応させる
- 不要な外部ブランディング、依存関係の仮定、upstream 固有のフレーミングを削除する

目標は、ECC を他者のランタイムの薄いラッパーに変えることなく、再利用することです。

## 元の名前を保持するタイミング

以下のすべてが真の場合にのみ、元のスキル名を保持します：

- コントリビューションが直接ポートに近い
- 名前がすでに説明的で中立的である
- サーフェスが依然として upstream の概念のように振る舞う
- リポジトリにすでにより良い ECC ネイティブの名前がない

例：

- `nestjs-patterns` のようなフレームワーク名
- ベンダーの売り込みではなく、主題であるプロトコルまたは製品名

## 名前を変更するタイミング

ECC が元の作業を有意に拡張、狭小化、または再パッケージする場合、スキルの名前を変更します。

典型的なトリガー：

- ECC が実質的な新しい挙動、構造、またはガイダンスを追加する
- 元の名前がワークフロー先行ではなく、ベンダー先行またはコミュニティブランド先行である
- コントリビューションが既存の ECC サーフェスと重複し、より明確な境界を必要とする
- コントリビューションが、文字通りのポートではなく、ケイパビリティ、オペレーターワークフロー、またはポリシーレイヤーとして適合するようになった

例：

- 再利用可能なグラフプリミティブを `social-graph-ranker` として保持しつつ、より広範なワークフローレイヤーを `lead-intelligence` または `connections-optimizer` にする
- スコープが実質的に変わった場合、曖昧なインポートされた計画ラベルよりも `product-capability` のような ECC ネイティブの名前を優先する

## 依存関係ポリシー

ECC は、仕事を成し遂げる最も狭いネイティブサーフェスを優先します：

- 決定論的な制約のための `rules/`
- オンデマンドのワークフローのための `skills/`
- 長期のインタラクティブなツール境界が正当化される場合の MCP
- 決定論的なワンショット実行のためのローカルスクリプト/CLI
- リモート呼び出しが狭く、MCP を正当化しない場合の直接 API

主に、ユーザーに未検証のサードパーティパッケージをインストールまたは信頼するよう伝えるためだけに存在するスキルの出荷を避けます。

外部機能が保持する価値がある場合：

- 実践的な場合は、関連するロジックを ECC 内でベンダー化または再作成する
- または、統合をオプションのまま、外部として明確にマークして保持する
- 明示的な正当化なしに、新しい外部依存関係をデフォルトのパスにさせない

## レビューの質問

コントリビュートされたスキルをマージする前に、これらに答えます：

1. これは ECC における実際の再利用可能なサーフェスか、それとも別のツールのための単なるドキュメントか？
2. 現在の名前は依然として ECC 形状のサーフェスに一致するか？
3. この挙動の大部分を所有する ECC スキルがすでに存在するか？
4. 概念をインポートしているのか、それとも他者の製品アイデンティティをインポートしているのか？
5. ECC ユーザーは、upstream リポジトリを知らずにこのスキルの目的を理解できるか？

それらの答えが弱い場合は、さらに適応させるか、スコープを狭めるか、出荷しないでください。
