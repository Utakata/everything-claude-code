# フックバグの回避策

ECC のフックを多用するセットアップに影響しうる、現在の Claude Code のバグに対する、コミュニティで検証された回避策です。

このページは意図的に狭くしています：投機的またはサポートされていない設定アドバイスを繰り返すことなく、より長いトラブルシューティングサーフェスから最もシグナルの高い運用上の修正を集めています。これらは upstream の Claude Code の挙動であり、ECC のバグではありません。

## このページを使うタイミング

以下を具体的にデバッグしているときに、このページを使用します：

- それ以外は成功しているフック実行に対する誤った `Hook Error` ラベル
- 予想より早いコンパクション
- 認証済みに見えるが、コンパクション後に失敗する MCP コネクター
- ホットリロードされないフックの編集
- 重いフック/ツールの圧力下での繰り返しの `529 Overloaded` レスポンス

より完全な ECC トラブルシューティングサーフェスについては、[TROUBLESHOOTING.md](./TROUBLESHOOTING.md) を使用してください。

## シグナルの高い回避策

### 誤った `Hook Error` ラベル

役立つこと：

- シェルフックの最初で stdin を消費する（`input=$(cat)`）。
- フックが明示的に構造化された stdout を必要としない限り、単純な allow/block フックでは stdout を静かに保つ。
- 人間が読める診断を stderr に送る。
- 正しい終了コードを使用する：`0` allow、`2` block、その他のゼロ以外の値はエラーとして扱われる。

```bash
input=$(cat)
echo "[BLOCKED] Reason here" >&2
exit 2
```

### 予想より早いコンパクション

役立つこと：

- ビルドで下げるとより早いコンパクションを引き起こす場合、`CLAUDE_AUTOCOMPACT_PCT_OVERRIDE` を削除する。
- 自然なタスク境界での手動の `/compact` を優先する。
- より低いしきい値を強制する代わりに、ECC の `strategic-compact` ガイダンスを使用する。

### MCP 認証がライブに見えるが、コンパクション後に失敗する

役立つこと：

- コンパクション後に、影響を受けるコネクターをオフにして再びオンにする。
- Claude Code のビルドがサポートしている場合、コネクター認証を再チェックするよう伝える軽量な `PostCompact` リマインダーフックを追加する。
- これを恒久的な修正ではなく、リカバリのリマインダーとして扱う。

### フックの編集がホットリロードされない

役立つこと：

- フックを変更した後、Claude Code セッションを再起動する。
- 上級ユーザーはシェルローカルのリロードヘルパーを使うことがあるが、それらのアプローチはシェルおよびプラットフォーム依存であるため、ECC は同梱していない。

### 繰り返しの `529 Overloaded`

役立つこと：

- セットアップがサポートしている場合、`ENABLE_TOOL_SEARCH=auto:5` でツール定義の圧力を減らす。
- ルーチンワークのために `MAX_THINKING_TOKENS` を下げる。
- セットアップがそのノブを公開している場合、サブエージェントの作業を `CLAUDE_CODE_SUBAGENT_MODEL=haiku` のようなより安価なモデルにルーティングする。
- 未使用の MCP サーバーをプロジェクトごとに無効化する。
- 自動コンパクションを待つ代わりに、自然なブレークポイントで手動でコンパクトする。
