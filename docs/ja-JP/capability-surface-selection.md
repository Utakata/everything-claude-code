# ケイパビリティサーフェスの選択

ケイパビリティがルール、スキル、MCP サーバー、または単純な CLI/API ワークフローのどれに属するかを決定するときの、ルーティングガイドとしてこれを使用します。

ECC はこれらのサーフェスを互換なものとして扱いません。目標は、各ケイパビリティを、正しさを保ち、トークンコストを制御下に保ち、不要なランタイムまたはサプライチェーンの負担を作らない、最も狭いサーフェスに置くことです。

## 短縮版

- `rules/` は、パスまたはイベントが一致したときに注入されるべき、決定論的で常時オンの制約のためのものです。
- `skills/` は、関連する場合にのみロードされるべき、オンデマンドのワークフロー、より豊かなプレイブック、トークンコストの高いガイダンスのためのものです。
- `MCP` は、セッションまたはクライアントをまたいだ長期のツール/リソースサーフェスから恩恵を受ける、インタラクティブな構造化ケイパビリティのためのものです。
- ローカルの `CLI` またはリポジトリスクリプトは、永続サーバーを必要としない、単純な決定論的アクションのためのものです。
- スキル内の直接 `API` 呼び出しは、完全な MCP サーバーが問題よりも重くなる、狭いリモートアクションのためのものです。

## 決定順序

これらの質問を順番に問います：

1. これはパスまたはイベントが一致するたびに、モデルの判断を伴わずに発生すべきか？
   - `rule` を使用する。
2. これは主にプレイブック、ワークフロー、またはアドバイザリレイヤーで、タスクが実際に必要とするときにのみロードされるべきか？
   - `skill` を使用する。
3. ケイパビリティは、複数のハーネスまたはクライアントが繰り返し呼び出すべき、構造化されたインタラクティブなツール/リソースインターフェースを必要とするか？
   - `MCP` を使用する。
4. これはサーバーを生かし続けずにスクリプトとして実行できる単純なローカルアクションか？
   - ローカルの `CLI` エントリポイントまたはリポジトリスクリプトを使用し、必要ならスキルでラップする。
5. これはより大きなワークフロー内の1つの狭いリモート統合ステップにすぎないか？
   - スキルまたはスクリプトから外部 `API` を直接呼び出す。

## サーフェスごとのガイダンス

### ルール

ルールを以下に使用します：

- パスをスコープとするコーディング不変条件
- 安全性の床と権限の制約
- 常に適用されるべきハーネス/ランタイムの制約
- モデルの裁量に依存すべきでない決定論的なリマインダー

ルールを以下に使用しないでください：

- すべての一致する編集を肥大化させる大きなプレイブック
- オプションのワークフロー
- 一部の時間だけ重要な、コストの高いドメインコンテキスト

### スキル

スキルを以下に使用します：

- マルチステップのワークフロー
- 判断の重いガイダンス
- オンデマンドでのみロードするのに十分コストの高いドメインプレイブック
- スクリプト、API、MCP ツール、隣接するスキルにまたがるオーケストレーション

本当は決定論的なルーティングを望む静的な不変条件のための投棄場としてスキルを使用しないでください。

### MCP

ケイパビリティが以下から恩恵を受ける場合に MCP を使用します：

- 構造化されたツールの入出力
- 再利用可能なリソースまたはプロンプト
- 繰り返されるクロスクライアントの使用
- Claude Code、Codex、Cursor、OpenCode、関連するハーネスをまたいで機能すべき安定したインターフェース
- 運用オーバーヘッドに値する長期のサーバープロセス

以下の場合は MCP を避けます：

- 仕事がワンショットのローカルコマンドである
- サーバーが行う唯一のことが一度シェルアウトすることである
- サーバーが製品価値よりも多くのインストール/ランタイムの負担を追加する

### CLI / リポジトリスクリプト

以下の場合にローカルスクリプトまたは CLI を優先します：

- アクションが決定論的である
- 起動が安価である
- ワークフローが主にローカルである
- 永続的なツール/リソースサーフェスを公開する利点がない

これはしばしば以下に適した選択です：

- lint/test/build のラッパー
- ローカルの変換
- 小さなインストーラー
- 呼び出しごとに一度実行されるコンテンツ生成

### 直接 API 呼び出し

以下の場合に、既存のスキルまたはスクリプト内の直接 API 呼び出しを優先します：

- 統合が狭い
- リモートアクションがより大きなワークフローの一部である
- まだ再利用可能なトランスポートサーフェスを必要としない

同じリモート統合が中心的で、繰り返され、マルチクライアントになった場合、それを MCP サーフェスに昇格させるシグナルです。

## コストと信頼性のバイアス

2つの選択肢が両方とも実行可能な場合：

- より小さなランタイムサーフェスを優先する
- より低いトークンオーバーヘッドを優先する
- より少ない外部の可動部分を持つパスを優先する
- 別のサードパーティ依存関係を導入するよりも ECC ネイティブのパッケージングを優先する

ケイパビリティがメンテナンス、セキュリティ、インストールの負担に明らかに値しない限り、外部プラグインまたはパッケージの依存関係をファーストクラスの ECC サーフェスとして常態化しないでください。

## リポジトリポリシー

外部リポジトリからアイデアを取り込むとき：

- 外部依存関係ではなく、根底にあるアイデアをコピーする
- それを ECC ネイティブのルール、スキル、スクリプト、または MCP サーフェスとして再パッケージする
- 機能が ECC 用に実質的に拡張または再形成された場合、名前を変更する
- その依存関係が意図的で、監査済みで、ワークフローの中心でない限り、ユーザーに無関係なサードパーティパッケージのインストールを要求する指示の出荷を避ける

## 例

- `api/**` の編集に常に適用されるべきバックエンド認証の不変条件：
  - `rule`
- より深い API 設計とページネーションのプレイブック：
  - `skill`
- 複数のハーネスをまたいで使用される再利用可能なリモート検索サーフェス：
  - `MCP`
- ローカルファイルを読んでレポートを書く、ワンショットのリポジトリアナライザー：
  - ローカルの `CLI` またはスクリプト、オプションで `skill` でラップ
- より広範な customer-ops ワークフロー内の1つの billing-portal セッション作成ステップ：
  - ワークフロー内の直接 `API` 呼び出し

## 実践的なヒューリスティック

不確かな場合は、より小さく始めます：

- 決定論的な不変条件には `rule` から始める
- ガイダンス/ワークフローには `skill` から始める
- ワンショット実行にはスクリプトから始める
- 構造化されたサーバー境界が明らかに元を取っている場合にのみ `MCP` に昇格する
