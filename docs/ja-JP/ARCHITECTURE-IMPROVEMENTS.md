# アーキテクチャ改善の推奨

このドキュメントは、Everything Claude Code (ECC) プロジェクトのためのアーキテクトレベルの改善をまとめます。保守性、一貫性、長期的な品質の向上を目指す Claude Code コーディングアーキテクトの視点から書かれています。

---

## 1. ドキュメントと単一の真実のソース

### 1.1 エージェント / コマンド / スキルのカウント同期

**問題：** AGENTS.md は「13 の専門エージェント、50 以上のスキル、33 のコマンド」と述べていますが、リポジトリには **16 のエージェント**、**65 以上のスキル**、**40 のコマンド**があります。README やその他のドキュメントも異なります。これはコントリビューターとユーザーに混乱を引き起こします。

**推奨：**

- **単一の真実のソース：** カウント（およびオプションでテーブル）をファイルシステムまたは小さなマニフェストから導出する。選択肢：
  - **オプション A：** `agents/*.md`、`commands/*.md`、`skills/*/SKILL.md` をスキャンして JSON/Markdown を出力するスクリプト（例：`scripts/ci/catalog.js`）を追加する。CI とドキュメントがこれを消費できる。
  - **オプション B：** エージェント、コマンド、スキルをメタデータとともにリストする1つの `docs/catalog.json`（または YAML）を維持する；スクリプトとドキュメントがそこから読む。追加/削除時に更新する規律が必要。
- **短期：** AGENTS.md、README.md、CLAUDE.md を実際のカウントと手動で同期し、新しいエージェント（例：chief-of-staff、loop-operator、harness-optimizer）をエージェントテーブルにリストする。

**影響：** 高 — 第一印象とコントリビューターの信頼に影響する。

---

### 1.2 コマンド → エージェント / スキル マップ

**問題：** 「どのコマンドがどのエージェントまたはスキルを使用するか」の、機械または人間が読める単一のマップがありません。これは README テーブルと個々のコマンド `.md` ファイルに存在し、ドリフトしうます。

**推奨：**

- 各コマンドについて、name、description、主要エージェント、参照されるスキルをリストする **コマンドレジストリ**（例：`docs/` 内、またはコマンドファイルのフロントマターとして）を追加する。コマンドファイルのコンテンツから生成するか、手動で維持できる。
- 発見可能性と（例：「どのコマンドが tdd-guide を使うか？」）ツーリングのために、ドキュメント（例：`docs/COMMAND-AGENT-MAP.md`）または生成されたカタログで「マップ」を公開する。

**影響：** 中 — 発見可能性とリファクタリングの安全性を向上させる。

---

## 2. テストと品質

### 2.1 テスト発見 vs ハードコードされたリスト

**問題：** `tests/run-all.js` はテストファイルの **ハードコードされたリスト** を使用します。新しいテストファイルは、誰かが `run-all.js` を更新しない限り実行されないため、カバレッジが省略によって不完全になりうます。

**推奨：**

- **glob ベースの発見：** パターン（例：`tests/` 配下の `**/*.test.js`）でテストファイルを発見して実行し、特殊なケースにはオプションの allowlist/denylist を用いる。これにより、新しいテストが自動的にスイートの一部になる。
- 発見されたテストを実行し、結果を集約する単一のエントリポイント（`tests/run-all.js`）を保つ。

**影響：** 高 — 新しいテストが存在するが決して実行されないというリグレッションを防ぐ。

---

### 2.2 テストカバレッジメトリクス

**問題：** カバレッジツール（例：nyc/c8/istanbul）がありません。プロジェクトは自身のスクリプトについて「80% 以上のカバレッジ」を主張できません；カバレッジは暗黙的です。

**推奨：**

- Node スクリプトのカバレッジツール（例：`c8` または `nyc`）を導入し、CI で実行する。ベースライン（例：60%）から始め、時間とともに引き上げる；または少なくとも失敗させずに CI でカバレッジを報告し、チームがトレンドを見られるようにする。
- 主要ターゲットとして `scripts/`（lib + hooks + ci）に焦点を当てる；必要なら1回限りのスクリプトを除外する。

**影響：** 中 — プロジェクトを自身の AGENTS.md ガイダンス（80% 以上のカバレッジ）に整合させ、テストされていないパスを表面化する。

---

## 3. スキーマと検証

### 3.1 CI で Hooks JSON スキーマを使用する

**問題：** `schemas/hooks.schema.json` が存在し、フック設定の形を定義しますが、`scripts/ci/validate-hooks.js` はそれを **使用しません**。検証は重複しており（VALID_EVENTS、構造）、スキーマからドリフトしうます。

**推奨：**

- `validate-hooks.js` で JSON スキーマバリデーター（例：`ajv`）を使用して、`hooks/hooks.json` を `schemas/hooks.schema.json` に対して検証する。バリデーターを構造の単一の真実のソースとして保つ；スクリプトにはフック固有のチェック（例：インライン JS 構文）のみを保持する。
- スキーマとバリデーターが同期を保つことを保証し、hooks.json の `$schema` を通じた IDE/エディター検証を可能にする。

**影響：** 中 — ドリフトを減らし、フック編集時のコントリビューター体験を向上させる。

---

## 4. クロスハーネスと i18n

### 4.1 スキル/エージェントのサブセット同期（.agents/skills、.cursor/skills）

**問題：** `.agents/skills/`（Codex）と `.cursor/skills/` は `skills/` のサブセットです。メインリポジトリでスキルを追加または削除するには、これらのサブセットを手動で更新する必要があり、忘れられうます。

**推奨：**

- スキルの追加が `.agents/skills` と `.cursor/skills` の更新を必要とする可能性がある（およびその方法）ことを CONTRIBUTING.md に文書化する。
- オプション：`skills/` をサブセットと比較し、スキルが一方のセットにあるが、あるべきなのに他方にない場合（例：規約または小さなマニフェストによる）に失敗または警告する CI チェックまたはスクリプト。

**影響：** 低〜中 — クロスハーネスのドリフトを減らす。

---

### 4.2 翻訳ドリフト（docs/ zh-CN、zh-TW、ja-JP）

**問題：** `docs/` の翻訳は、エージェント、コマンド、スキルを重複させます。英語ソースが進化するにつれて、明確なプロセスやツーリングなしに翻訳が古くなりうます。

**推奨：**

- **翻訳プロセス** を文書化する：いつ更新するか（例：リリース時）、各ロケールを誰が所有するか、stale なコンテンツをどのように検出するか（例：ファイルリストの diff またはキーセクション）。
- 検討：翻訳ステータスファイル（例：`docs/i18n-status.md`）、または翻訳ファイルの存在/タイムスタンプをチェックし、英語が翻訳よりも最近更新された場合に警告する CI。
- 長期：翻訳が英語ソースと同じ構造を参照するよう、抽出/プレースホルダー形式（例：i18n キー）を検討する。

**影響：** 中 — 非英語ユーザーの体験を向上させ、古い翻訳による混乱を減らす。

---

## 5. フックとスクリプト

### 5.1 フックランタイムの一貫性

**問題：** フックは一貫した Node モードのディスパッチサーフェスを保つべきです。Continuous-learning の観測は現在、`run-with-flags.js` と `observe-runner.js` を通じてディスパッチし、シェルモードのフックエントリを公開せずに既存の `observe.sh` 実装に委譲します。

**推奨：**

- 可能な場合、新しいフックには Node を優先する（クロスプラットフォーム、単一ランタイム）。シェルが必要な場合は、理由を文書化し、サーフェスを小さく保つ。
- 挙動が一貫するよう、すべてのコードパス（シェルを含む）で `ECC_HOOK_PROFILE` と `ECC_DISABLED_HOOKS` が尊重されることを保証する。

**影響：** 低 — 現在の設計を維持する；より多くのフックが Node に移行すれば改善する。

## 6. サマリーテーブル

| 領域              | 改善                          | 優先度 | 労力  |
|-------------------|--------------------------------------|----------|---------|
| ドキュメント同期          | AGENTS.md/README のカウント & テーブルを同期 | 高     | 低     |
| 単一のソース     | カタログスクリプトまたはマニフェスト           | 高     | 中  |
| テスト発見    | glob ベースのテストランナー               | 高     | 低     |

| CI のフックスキーマ | スキーマ経由で hooks.json を検証       | 中   | 低     |
| コマンドマップ       | コマンド → エージェント/スキルのレジストリ       | 中   | 中  |
| サブセット同期       | .agents/.cursor のドキュメント/CI       | 低〜中  | 低〜中 |
| 翻訳      | プロセス + stale 検出             | 中   | 中  |
| フックランタイム      | Node を優先；シェル使用を文書化       | 低      | 低      |

## 7. クイックウィン（即時）

1. **AGENTS.md を更新：** エージェント数を16に設定する；chief-of-staff、loop-operator、harness-optimizer をエージェントテーブルに追加する；スキル/コマンドのカウントをリポジトリに整合させる。
2. **テスト発見：** 新しいテストが常に実行されるよう、`run-all.js` を `tests/` 配下の `**/*.test.js` を発見する（オプションの allowlist 付き）ように変更する。
3. **フックスキーマを配線：** `validate-hooks.js` で、ajv（または類似）を使用して `hooks/hooks.json` を `schemas/hooks.schema.json` に対して検証し、スクリプトにはフック固有のチェックのみを保持する。

これら3つは1〜2セッションで完了でき、一貫性と信頼性を実質的に向上させます。
