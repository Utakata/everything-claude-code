# スキル品質エビデンスプレイブック

候補ID：`evidence-backed-skill-amendment`

PRまたはフォローアップが、スキル、エージェント、コマンド、またはルールのガイダンスサーフェスの
追加、書き換え、または修正を提案する場合に、このプレイブックを使用します。

## 承認パス

1. 変更されたガイダンスサーフェスとソースファイルを特定する。
2. `docs/SKILL-DEVELOPMENT-GUIDE.md` から品質契約を取得する。
3. 提案された変更を、`skills/*/SKILL.md` 配下の近い焦点の絞られた例と比較する。
4. 変更を正当化するエビデンスソースを記録する：
   - 観測されたスキル実行の失敗；
   - ユーザーフィードバック；
   - 繰り返されるレビュー指摘；
   - リファレンスセットのギャップ；
   - 失敗する例またはリグレッションテスト。
5. スコープを狭く保つ。1つのスキルは1つのドメイン、ワークフロー、
   または再利用可能なパターンをカバーすべきです。
6. 検証可能な場合にのみ、例を追加または更新する。
7. 関連する検証ゲートを実行する：
   - `node scripts/ci/validate-skills.js`
   - `node tests/lib/skill-improvement.test.js`
   - `node tests/lib/skill-evolution.test.js`
   - `npm run catalog:check`
   - 例を変更した場合は、`npx tsc --noEmit`、`python -m py_compile`、`go build` などの
     言語固有の例コマンド。
8. 検証出力、ソースアトリビューション、およびロールバックノートを、
   メンテナーのPR本文またはハンドオフに記録する。

## 却下パス

観測された失敗のエビデンス、例、またはリファレンスセットなしに、文章が「より良く聞こえる」という理由で
曖昧なスキルの書き換えを昇格させないこと。

焦点の絞られたスキルを重複させたり、アクティベーションの予測可能性を下げたりする
マルチドメインのcatch-allスキルをマージしないこと。

プライベートなオペレーターコンテキスト、シークレット、トークン、個人のパス、顧客データ、
または未公開のリリース主張をスキルにコピーしないこと。

エバリュエーターの実行から、パッケージマニフェスト、プラグインマニフェスト、カタログ、
リリースノート、または公開状態を更新しないこと。

## 最小限の検証

- `node scripts/ci/validate-skills.js`
- カタログ/パッケージに見えるスキルサーフェスが変更される場合は `npm run catalog:check`
- 修正の挙動が変わる場合は、焦点を絞ったskill-improvementまたはskill-evolutionの
  リグレッションテスト
- 変更された例に対する言語固有のコンパイル/lintチェック
- `git diff --check`
- ドキュメントまたはプレイブックを変更した場合はMarkdown lint

コントリビュートされたスキル素材のソースアトリビューションを保持し、将来のメンテナーPRのために
ロールバックガイダンスを含めること。
