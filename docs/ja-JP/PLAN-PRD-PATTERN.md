# Plan-PRD パターン：Markdown ステージングによる計画フロー

各ライフサイクルフェーズが、次のコマンドが消費するコミット可能な Markdown **ステージングファイル** を生成する、軽量で SDLC に整合した計画ワークフロー。

> 短縮版：`/plan-prd` が PRD を書き、`/plan` がプランを書き、`tdd-workflow` スキルがそれを実装し、`/pr` がそれを出荷します。各矢印は、メモリ内の会話ではなく、ディスク上のファイルです。

## 機能：Markdown ステージングファイル

すべての計画アーティファクトは、`.claude/` 配下の単純な `.md` ファイルです：

```
.claude/
  prds/      # /plan-prd からの Product Requirements Documents
  plans/     # /plan からの実装プラン
  reviews/   # /code-review からのコードレビューアーティファクト
```

これらのファイルは：

- **単純な markdown** — 人間が読め、PR で diff でき、CLI で grep できる。
- **コミット可能** — コードと一緒にチェックインし、意図が実装とともに移動する。
- **合成可能** — 各コマンドが前のステージのファイルを `$ARGUMENTS` として受け取り、ツールチェーンはコンテキスト内の状態ではなくパスを通じて合成される。
- **再開可能** — セッションを閉じ、明日新しいものを開き、ファイルパスを渡し戻す。

## フロー

```
┌───────────────────────────┐
│ /plan-prd "<idea>"        │  要件フェーズ
│  → .claude/prds/X.prd.md  │   Problem · Users · Hypothesis · Scope
└─────────────┬─────────────┘
              │
              ▼
┌───────────────────────────┐
│ /plan <prd-path>          │  設計フェーズ
│  → .claude/plans/X.plan.md│   Patterns · Files · Tasks · Validation
└─────────────┬─────────────┘
              │
              ▼
┌───────────────────────────┐
│ tdd-workflow skill         │  実装フェーズ
│  → code + tests           │   テストファースト、最小の差分
└─────────────┬─────────────┘
              │
              ▼
┌───────────────────────────┐
│ /pr                        │  デリバリーフェーズ
│  → GitHub PR               │   PRD + プランにリンクバック
└───────────────────────────┘
```

各ボックスは **ゲート** です。以下ができます：

- ゲート間で停止する — アーティファクトは永続する。
- アーティファクトパスを使用して任意のゲートから再開する。
- 小さな作業ではゲートをスキップする — `/plan` に自由形式のテキストを与え、`/plan-prd` を無視する。
- ゲートをスタンドアロンで実行する — `/plan "refactor X"` はアーティファクトなしで会話的なプランを生成する。

## なぜ `/plan-prd` が `/plan` に追加されるのか

これらは異なる質問に答えます。混ぜるとスコープクリープを引き起こします。

| コマンド | 答えること | SDLC フェーズ | アーティファクト |
|---|---|---|---|
| `/plan-prd` | *どんな問題？ 誰のため？ 完了をどう知るか？* | 要件 | `.claude/prds/{name}.prd.md` |
| `/plan` | *どのファイル、パターン、タスクが要件を満たすか？* | 設計 + 実装戦略 | `.claude/plans/{name}.plan.md`（PRD モード）またはインライン（テキストモード） |

### なぜそれらを結合しないのか？

- **関心の分離。** PRD は *なぜ* を問う；プランは *どのように* を問う。それらをバンドルすると、両方をうまくこなせない1つの過大なコマンドが作られる。これは、古い `/prp-prd` → `/prp-plan` のペアが示したとおり（実装フェーズのテーブルが要件に混ざった8フェーズの尋問）。
- **異なる対象者。** PRD をレビューするステークホルダーは、ファイルパスや型チェックコマンドを気にしない。プランを読むエンジニアは、市場調査フェーズを必要としない。
- **異なる寿命。** PRD は、実装の仮定が変わるにつれてそのプランが複数回書き換えられる間、安定したままでいられる。
- **オプションのステップ。** 多くの変更（バグ修正、小さなリファクタリング、単一ファイルの追加）は PRD を必要としない。`/plan` だけで十分。すべての変更に PRD を強制するのは官僚主義。

### それぞれを使うタイミング

`/plan-prd` を以下の場合に使用します：

- スコープが不明確または争われている。
- 解決策の前に、複数のステークホルダーが問題について整合する必要がある。
- 変更が十分大きく、仮説を書き留める方が、実装途中でスコープを再議論するよりも安価。

`/plan` を直接以下の場合に使用します：

- 要件がすでに明確（バグレポート、スコープの定まったリファクタリング、既知の移行）。
- 作業が十分小さく、会話的なプラン + 確認ゲートで十分。
- すでに PRD がある — それを `/plan` に渡し、`/plan-prd` をスキップする。

## 使用法

### フルフロー（スコープが不明確な機能）

```bash
# 1. PRD を起草する
/plan-prd "Per-user rate limits on the public API"

# → .claude/prds/per-user-rate-limits.prd.md が作成される
# フレーミングの質問に答え、エビデンスを提供し、仮説とスコープを定義する。

# 2. 次の pending マイルストーンを選び、プランを生成する
/plan .claude/prds/per-user-rate-limits.prd.md

# → .claude/plans/per-user-rate-limits.plan.md が作成される
# プランには、ミラーするパターン、変更するファイル、検証コマンドが含まれる。
# PRD の Delivery Milestones テーブルは、選択された行を `in-progress` に更新する。

# 3. テストファーストで実装する
Use the tdd-workflow skill

# 4. PR を開く
/pr
# → PR 本文が .claude/prds/... と .claude/plans/... を自動参照する
```

### クイックフロー（スコープがすでに明確）

```bash
/plan "Add retry with exponential backoff to the notifier"
# 会話的な計画、アーティファクトなし。
# 確認してから、tdd-workflow スキルを使用する。
```

### 別の場所から既存の PRD を参照する

```bash
# PRD は他の誰かが書き、あなたのリポジトリに存在する
/plan docs/rfcs/0042-rate-limiting.prd.md
```

`/plan` は任意の `.prd.md` パスを検出し、アーティファクトモードに切り替え、Delivery Milestones テーブルをパースします。

## なぜステージングファイルがコンテキスト内の状態に勝るのか

- **転送可能**：PRD パスを新しいセッションに入れれば追いつける — 長い会話を再生する必要がない。
- **監査可能**：PR レビュアーが *あなたが意図したこと* を *あなたが作ったこと* の隣で見る。
- **バージョン管理**：ステージングファイルはコードと同じように git 履歴で進化する。
- **機械パース可能**：`/plan` はプログラム的に次の pending マイルストーンを選ぶ；`/pr` はプログラム的に PR 本文でアーティファクトをリンクする。プロンプトエンジニアリング不要。

## 関連コマンド

- `/plan-prd` — 要件（このパターンのエントリポイント）。
- `/plan` — 計画（PRD または自由形式のテキストを消費）。
- `tdd-workflow` スキル — テストファーストの実装。
- `/pr` — PRD とプランを参照する PR を開く。
- `/code-review` — ローカルの差分または PR をレビューする；`.claude/prds/` と `.claude/plans/` をコンテキストとして自動検出する。

## 互換性

このパターンは、既存の `prp-*` コマンドセットと並んで ECC ネイティブのステージングファイルコマンドを追加します。レガシーの PRP コマンドは、より深い PRP ワークフローと、すでに `.claude/PRPs/` アーティファクトを持つユーザーのために引き続き利用可能です。

- `/plan-prd` は `.claude/prds/` のための無駄のない要件エントリポイント。
- `/plan` は `.prd.md` ファイルを消費し、レガシーの PRP ディレクトリレイアウトを要求せずに `.claude/plans/` アーティファクトを生成できる。
- `/pr` は ECC ネイティブの PR 作成コマンドで、`.claude/prds/` と `.claude/plans/` を参照できる。
- `/prp-prd`、`/prp-plan`、`/prp-implement`、`/prp-commit`、`/prp-pr` は、有効なレガシー/深いワークフローのコマンドのままです。
